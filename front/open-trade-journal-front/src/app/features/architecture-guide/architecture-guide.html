Trade Journal Architecture

Explore how the frontend, backend, authentication, database, and real-time trading infrastructure work together.

01 What is the overall architecture of Trade Journal? expand_more

Trade Journal is built as a modern full-stack application using Angular for the frontend and Spring Boot for the backend.

Authentication and authorization are handled through Keycloak using the OAuth 2.0 / OpenID Connect protocols. Real-time trade events are distributed through Apache Kafka.

02 How does authentication work? expand_more

Trade Journal uses Keycloak as the centralized identity and access management system.
The Angular application does not directly manage user passwords. Instead, users are redirected to Keycloak to authenticate. Keycloak then issues the required authentication tokens.
The application uses OAuth 2.0 and OpenID Connect to establish the authenticated user session and securely communicate the user's identity.

> User opens Trade Journal
> Angular redirects to Keycloak
> User authenticates
> Keycloak issues tokens
> Angular uses the access token for API requests
> Spring Boot validates the request
SECURITY Authentication is centralized in Keycloak, allowing the application backend to protect its APIs without storing user credentials directly.

04 What is responsible for the backend? expand_more

The backend is implemented using Spring Boot.
It exposes REST APIs used by the Angular frontend and contains the application's business logic, trade processing, persistence, evaluation management and integration with the real-time messaging infrastructure.

> Angular HTTP request
> Spring Boot REST Controller
> Service / Business Logic
> Repository / Persistence
> Database

Spring Boot also acts as the security boundary for protected backend resources by validating authenticated requests.

05 How is Apache Kafka used for real-time trading? expand_more

Apache Kafka is used as the event-streaming layer for real-time trading updates.
Instead of the frontend continuously polling the backend for new trades, trade events can be published to Kafka and processed asynchronously by the backend.

01 IBKR / TWS Trade execution
02 Trade Producer Publishes event
03 Kafka Event stream
04 Spring Boot Consumes event
05 Angular Real-time update
> Trade executed in IBKR / TWS
> Trade event is produced
> Kafka receives the event
> Spring Boot consumes the event
> Trade is processed and persisted
> Frontend receives the update
> UI updates without manual refresh
> WHY KAFKA? Kafka decouples trade producers from consumers and provides a reliable event-streaming mechanism for processing trading events asynchronously.
06 What happens to a trade event inside Kafka? expand_more

A trade event is published to a Kafka topic. Kafka stores the event in the topic so that one or more consumers can process it.

01 Producer

Creates and publishes a trade event.

02 Kafka Topic

Receives and stores the event stream.

03 Consumer

Spring Boot consumes the trade event.

04 Processing

The application processes and persists the trade.

This architecture separates the system that produces trading events from the services that consume and process them.
